# Wallet: implementation plan

Personal finance manager covering salary, extra income, monthly and yearly subscriptions, budgets with optional rollover, spendings, savings and savings goals.

- **Stack**: Node 24 · Express 5 · Drizzle ORM · SQLite (better-sqlite3) · Angular 22 (zoneless, signals) · Tailwind CSS v4 · zod · vitest.
- **Specification**: [`DOMAIN.md`](./DOMAIN.md) is the source of truth for every calculation.
- **Agents**: `.claude/agents/` defines `backend-engineer`, `frontend-engineer`, `finance-domain-reviewer` and `test-engineer`.

---

## Architecture

```
browser ──HTTP──▶ Express (one Node process, port 3400)
                   ├─ /api/*   JSON API ─▶ services ─▶ ledger engine (pure) ─▶ Drizzle ─▶ SQLite file
                   └─ /*       built Angular app (production)
```

- **Monorepo** with npm workspaces: `shared/` (API contract and pure helpers, consumed as TS source), `backend/` and `frontend/`.
- **Derived ledger.** The database stores facts only (salary history, incomes, subscriptions, budgets, spendings, transfers and savings transactions). All balances, carry-overs, reserves and savings due are computed by one pure function, `computeLedger(facts, throughMonth, today)` in `backend/src/domain/ledger.ts`. This means:
  - there is no cron job or "close month" process that can fail, run twice or be skipped
  - late edits flow through correctly
  - everything is unit-testable without a database
  - at personal scale (hundreds of months × tens of budgets) recomputing on each request costs well under a millisecond, so caching can wait until it's measured.
- **Versioned values** (salary, budget amount and mode, subscription price) mean history never changes by accident.
- **No auth** (single user, by decision). Run it on a LAN or VPN only. [Tailscale](https://tailscale.com) is the easiest option, and `tailscale serve` also provides the HTTPS that the PWA needs.

## Phase 1 · Core data API (`backend-engineer`) ✅

Contracts go in `shared/src/<feature>.ts` first, so the frontend can start in parallel. **The Phase 1 contracts and the Phase 2 month read model are written** (`settings`, `onboarding`, `salary`, `incomes`, `budgets`, `subscriptions`, `spendings`, `months`, plus the error and paging types in `api.ts`). ### API conventions

- **Status codes**: create → 201 + DTO. Read, `PATCH`, upsert (`PUT`) and the action `POST`s (`archive`, `cancel`) → 200 + DTO. `DELETE` → 204 with no body.
- **Lists** are arrays in the order documented on the DTO. Spendings return a `Page<T>` (`items`, `total`, `limit`, `offset`) instead.
- **`PATCH`**: every field optional, at least one required. `null` clears a nullable field. Unknown fields are rejected (`z.strictObject`).
- **Ids** are integers, **dates** `YYYY-MM-DD`, **months** `YYYY-MM`, **money** integer cents. DTOs carry no `createdAt`/`updatedAt`.
- **Time**: the UI gets "today" from `GET /api/today` (server clock and `TZ`), never from the browser.
- **Errors** always have the shape `{ error: { code, message, details? } }`. `code` is an `ApiErrorCode` and fixes the status:

## Phase 5 · Transfers, tags and search (backend + frontend) ✅

**Done, and the reviewer's gate passed.** The contracts are `shared/src/transfers.ts`, `shared/src/tags.ts` and the additions to `shared/src/spendings.ts` (with the new code `tag_name_taken` and the new rule `unknown_tag` in the tables above). Every endpoint below is implemented (`modules/transfers`, `modules/tags` and the `tagIds` and search additions to `modules/spendings`) and so is the UI. The rules are in [`DOMAIN.md`](./DOMAIN.md#transfers) and [`DOMAIN.md`](./DOMAIN.md#tags-and-search), and the conventions are the Phase 1 ones. No migration was needed: `budget_transfers`, `tags` and `spending_tags` exist since `0000_init`. SQLite's `unique` on `tags.name` is exact-case, so the service enforces the name rule itself (`backend/src/lib/names.ts`), and SQLite's `LIKE` and `lower()` fold only ASCII, so the search folds the case itself (`backend/src/lib/fold.ts`, registered as the SQL function `fold_text` in `createDb`).

**The `finance-domain-reviewer` signed off the backend** with no finding at medium severity or higher. It used its own oracle, an HTTP fuzzer (about 21,600 verified steps in five time zones, over every operation that touches the transfer guards) and an exhaustive search of every three-operation sequence over 76 boundary-heavy operations. No sequence of API calls leaves a stored transfer that the ledger would ignore, a transfer dated in a month X never moves a month before X, and deleting a transfer puts every month, summary and savings entry back to the cent. Four low-severity notes, all handled: (1) a transfer dated beyond the 120-month horizon is accepted, as a spending is, but it is then in no month view and pins its budget (`end_before_activity`, `has_history`), so the dialog now limits its date to `startMonth` through the current month plus 120, and the API's behavior is written down in DOMAIN; (2) a tag name made only of invisible characters was accepted, and is now a 400 at `name`; (3) an outstanding amount above `MAX_CENTS` can't be settled, which is the Phase 4 limit above: two transfers of `MAX_CENTS` (10 billion each) into an incremental budget of a closed month reach it, so it stays as it is; (4) the tag-name wording of this file now follows DOMAIN. Calls made while implementing, now written in DOMAIN: tag names clash under the shared name collator, which is wider than case (Unicode normalization, full-width and ligature forms, invisible characters), and the search fold is specified to the letter (`ß` finds `ss`, dotless `ı` finds `i`, the typographic ligatures `ﬁ` and `ﬃ` are found by their letters, accents are never stripped).

**Tests.** Route tests for every endpoint (each 400, 404, 409 and 422 in the documented order, and the effect on the month view to the cent); independent scenario tests (`modules/transfers/transfers.*.scenario.test.ts`: every kind in a closed, the current and a future month, settle and adjustment, undo, delete back to the cent, the cross-mode and last-month cases); an operation fuzz against an independent model (`transfers.fuzz.test.ts`); a model test of the search and filters; and a property that tags never change a number. The backend went from 1,386 to 2,059 tests and the frontend from 1,056 to 1,443. The UI was driven through a real browser against the real API (light, dark and 390 px wide, with axe-core reporting no violations in every state). That pass found and fixed 11 defects that unit tests could not see, among them focus lost after closing any dialog, the savings badge in the navigation not refreshing after a closed-month change, a tab trap in the tag suggestions, focus hidden under the sticky month bar, and an address with a raw `%` opening the Dashboard.

**Known gaps, outside this phase.** The savings badge in the navigation refreshes after a transfer and after a spending in a closed month, but not yet after edits on Income, Subscriptions and backdated budget changes. A malformed percent escape in a path outside `/api` (`/spend%ings`) answers 500 where 400 or 404 would do. The fuzz tests have no spending-edit (`PATCH`) operation.

Any month is allowed, a closed one too, and so is a date beyond the 120-month horizon that no month view shows (as for spendings), which is why the UI keeps its date picker inside the tracked range. Never refused for lack of money. |
| `DELETE /api/transfers/:id`               | 204, or 404. There is no `PATCH`: a transfer is deleted and entered again. A transfer dated in a closed month rewrites that month, when it is created and when it is deleted, so the UI confirms both.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `GET /api/tags`                           | `TagDto[]` `{ id, name, color, usageCount }`, ascending by name under the same comparison (case is ignored, accents are not), then by id. `usageCount` is the number of spendings that carry the tag.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `POST /api/tags`                          | `{ name, color? }` → 201 `TagDto`. The name is trimmed, 1 to 30 characters, and not made only of invisible characters (400 at `name`). 409 `tag_name_taken` when another tag has the same name under the comparison above.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `PATCH /api/tags/:id`                     | `{ name?, color? }`, at least one; `color: null` clears it. 200 `TagDto`. 400 for a name made only of invisible characters, 404, then 409 `tag_name_taken` (another capitalization of the tag's own name is fine).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `DELETE /api/tags/:id`                    | 204, or 404. Removes the tag from every spending that carries it. The spendings stay.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `POST` and `PATCH /api/spendings` (added) | Accept `tagIds`: at most 10, none twice (a 400 at `tagIds.<i>`). Each must exist: 422 `unknown_tag`, checked after the budget and date rules. On `PATCH` a given `tagIds` replaces the whole set, `[]` clears it, and leaving it out keeps it. `SpendingDto` gains `tagIds`, ascending by id, in every response that carries a spending.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `GET /api/spendings` (added)              | New filters `q` (1 to 100 characters after trimming; a case-insensitive substring of the description or the notes, with the case folded for every alphabet and the accents kept; `%` and `_` are plain characters), `tagId`, `minAmount` and `maxAmount` (signed cents as stored, so refunds are negative; `minAmount` above `maxAmount` is a 400). **What the domain review found and fixed.**

- **High:** `1 234,50€` (a thousands group with the currency glued on) was read as €1.00 with the note `234,50€`. The parser now refuses any whole number of 1 to 3 digits that is followed by a note starting with exactly three digits.
- **Stale buttons after a restore.** Row ids come back after a backup restore, so an old Undo could delete a different, newer spending. Every row button now carries a fingerprint (the row's `createdAt` in milliseconds, base 36) and a mismatch answers "Already removed.". It assumes the clock does not repeat a millisecond between a restored-away row and its replacement, which a restore always satisfies on a real clock.
- **Duplicate alert** beside the bot's own confirmation: the confirmed level is now recorded before the confirmation is sent, and given back if the confirmation never reaches the user.
- **The closed-month question** said "changes what is due to savings" for every budget, which is false for an incremental budget (its remainder is carried). It now follows the carry to where it stops (the first month that is not incremental or ends this month) and names that month, and the confirmation shows that month's line. A Change date inside one month asks nothing.
- A confirmed Delete, Remove or Change date re-checks the closed months at tap time. A write whose confirmation cannot be shown is never reported as "Nothing was changed". The recap is resent without its button only after a 400, not after a timeout.
- **The recap's "Due to savings"** now says what is really outstanding after a settlement was adjusted ("€600.00 already moved to savings, take €30.00 more from savings"), keyed on `adjustment` as the savings inbox is.
- **A budget that starts a month over** is announced at `notifyAt`, not at 00:01.

**Where the build differs from the plan.**

- The bot reads incomes with `updateIncome` too (Change date on an income).
- A reply to `/start <wrong code>` happens only while a code is open; otherwise the bot stays silent, as for any stranger.
- A thousands-grouped amount (`1 234,50`) and a currency other than `€` or the Settings currency are refused, never guessed.
- The preferences row is created by the first save (reads return `DEFAULT_TELEGRAM_NOTIFICATIONS` until then).
- A change to the alert write hook: it sits before the pre-onboarding routers, so a settings change (a new warning threshold) also asks for a check.

**Known gaps and questions for the owner.**

- **Not tried with a real bot.** Telegram's own wire behaviour is untested; the runtime was run once against a local fake Bot API. The first real link, spending, undo and reminder are still to be done on a phone (README, "Telegram bot").
- **Engineering decisions awaiting the owner** (marked as such in `DOMAIN.md`): the mode-based closed-month wording and the extra line for a carrying budget; a same-month Change date never asks, even in a closed month; carry-in alerts wait for `notifyAt`; the level recorded before the confirmation is sent.
- **One accepted race:** a real alert for the same level in flight at the moment of a bot write whose confirmation then fails on every send can be announced twice. It never shows a wrong figure and never loses an alert.
- Step 1 of `/spending` offers only the budgets active in the current month, while the date buttons reach 6 days back, so a budget that ended last month cannot get an entry dated in its last days (the service's 422 is turned into a message). Moving a spending from a carrying closed month into a settling closed month prints only the new month's line.
- Settings reads the bot status again after a refused test message, but a `conflict` or `unreachable` that starts while the page is open appears only after a reload. The "Expires" hint uses the browser's clock for display only.
- The scheduler's tick is a real one-minute timer with no override, so the e2e scenario for reminders and the recap waits for it (about 3 minutes).
- The running `wallet.service` was not rebuilt or restarted: it has none of this code until `npm ci && npm run build` and a restart. Migration `0003` then applies by itself. Take a backup first (an older version cannot open the migrated database).

## How to run a phase with the agents

1. `backend-engineer`: contracts in `shared/`, then schema/migration, endpoints and tests.
2. `frontend-engineer` (in parallel once the contracts exist): the pages for that phase.
3. `finance-domain-reviewer`, whenever money logic changed (always for Phases 2, 4 and 5).
4. `test-engineer`: scenario tests and E2E for what landed.
5. `npm run typecheck && npm test && npm run build` must be green before the phase is called done.
